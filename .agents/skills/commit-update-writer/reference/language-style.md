# CAM-FE Commitlog 文风参考

每次写入 `docs/COMMITLOG.md` 前必须阅读本文件。记录应是克制、可追溯的工程复盘，不是发布公告。

## 写作原则

1. 先说明为什么改：问题、约束、失败尝试或决策取舍；再说明如何实现。
2. 使用真实模块、函数、环境变量和命令，例如 `cam/App`、`setPlatformAuth`、`ApiError`、`VITE_CAM_PUBLIC_BASE_URL`、`/api`。代码标识使用反引号。
3. 按链路写作：上游（Pedestal host/平台合同）→ 当前改动 → 下游（请求层、服务、组件、翻译、remote 产物）。
4. 结论必须区分已验证、未验证与仍有风险；避免“完全解决”“没有风险”“显著提升”等无证据表述。
5. 中文为主，英文术语只用于精确表达。短句优先，复杂因果可用“因为…所以…；但…因此…”说明。

## 推荐叙述

```markdown
这次改动的起点是 CAM remote 的 <具体问题>。
一开始我们考虑 <方案>，但它会 <明确代价>，因此最终在 `<真实模块>` 中采用 <实际方案>。

上游依赖是 `<host 合同或 request 配置>`；当前改动 <实现>；下游的 `<服务或组件>` 因此 <真实结果>。
当前已通过 `<命令>` 验证 <范围>，但 <未验证范围> 仍需要 <后续动作>。
```

## 禁止写法

- 只贴 diff 或只列文件名。
- 只写“做了什么”，不解释问题与取舍。
- 将计划、推测或未获授权的后端/E2E 验证写成既成事实。
- 把 Pedestal host、请求层、服务与业务 UI 拆成互不相关的孤立改动。
